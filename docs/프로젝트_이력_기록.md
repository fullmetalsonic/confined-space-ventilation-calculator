## 1. 프로젝트 개요

밀폐공간 작업 프로그램 수립 시, 안전담당자가 작업 전(최초 급기)·작업 중(유지 환기) 필요환기량을 표준화된 방식으로 산정하고, 사업장이 보유한 송배풍기로 해당 환기량을 충족할 수 있는지 즉시 확인할 수 있도록 지원하는 계산 도구를 만드는 것이 목표였다. 법령·기술지침상 근거를 함께 제시해 작업허가서 첨부 자료로 쓸 수 있는 결과물을 지향했다.

## 2. 진행 경과 (요청 → 처리 내용 순서대로)

### 2-1. 배경 조사
밀폐공간 작업에 적용되는 산업안전 법·지침·가이드를 조사함.
- 법령: 산업안전보건법 제5·39·52조, 산업안전보건기준에 관한 규칙 제3편 제10장(제618~626조)
- 정의(제618조): 밀폐공간, 유해가스, 적정공기(산소 18~23.5%, CO₂ 1.5%미만, CO 30ppm미만, H₂S 10ppm미만), 산소결핍
- KOSHA GUIDE(기술지침): H-80-2021 「밀폐공간 작업 프로그램 수립 및 시행에 관한 기술지침」 등

### 2-2. 필요환기량 계산법 문의
밀폐공간 환기 중 "필요환기량"을 구하는 방법을 안내함.
- **체적배수법**: 실무 기준(작업 전 체적×배수, 작업 중 환기횟수×체적)
- **오염물질 희석법**: 이상기체 몰부피(24.45L/mol) 기반 희석환기 공식

### 2-3. 실시간 측정 기반 발생량 역산 아이디어
"현재 오염물질 발생량을 모를 때, 송풍 후 일정시간 지나 농도를 측정해 발생량을 역산할 수 있지 않냐"는 제안 → 질량보존식(1구획 모델) 기반 역산 공식 도출:

```
C(t) = Css + (C0 − Css)·e^(−Qt/V),   Css = G/Q
G = Q × [C(t) − C0·e^(−Qt/V)] / [1 − e^(−Qt/V)]
```

### 2-4. 기획안(Word) + 프로토타입(HTML) 제작 요청
- **기획서(docx)** 1차 작성 → LibreOffice로 PDF 변환 후 페이지 이미지 검토
- **HTML 계산기** 1차 제작 (6단계 마법사 구조: 계산방식 선택 → 체적산출 → 작업조건 → 계산결과 → 송배풍기매칭 → 결과리포트)
  - Playwright 헤드리스 브라우저로 전 단계 실행 + Python으로 수식 교차검증

### 2-5. 실무 기능 추가 요청
"정상상태 도달 예상시간 포함해서, 실무에 유용한 기능을 고민해서 추가해줘" → 브레인스토밍 후 아래 항목 선정·구현:
- 정상상태(목표농도) 도달 예상 시간 (희석법 B·C, 질량보존식 기반)
- 적정공기 기준 빠른 참조 패널
- 풍량 단위 변환기 (CMH·CMM·L/min·CFM)
- 용어 명확화 (예: "환기횟수=연속가동 기준이며 온오프 반복 아님"을 UI에 직접 명시)

### 2-6. "기본값 20회의 근거가 뭐냐" 질의
→ 원문 PDF(KOSHA GUIDE H-80-2021)를 직접 다운로드해 대조.
- **20회/h**: 9.1(1)항, 현재도 유효한 기준
- **최초 급기 배수**: 도구에 넣었던 "5배"가 **구버전**임을 발견. 원문 개정이력에 "환기실험·CFD 결과를 반영해 5배→10배로 상향(2021.12)"이라고 명시되어 있어 **10배로 정정**
- 도구의 기본값·힌트 문구를 원문 근거에 맞춰 수정

### 2-7. "법·가이드의 최소 권장사항임을 명확히 보여주고 있냐" 질의
→ 점검 결과 일부 미흡함을 확인하고 보완:
- 상단에 "법령 vs KOSHA 가이드 vs 사용자 입력값" 구분표 추가
- 입력 힌트·결과 라벨에 "이상"(최소 기준) 문구 명시, 수식도 `=` → `≥`로 표기

### 2-8. 기획서 + 실제 HTML 도구 제작
Word 기획서와 HTML 프로토타입을 순차 제작. Playwright로 3개 계산방식(체적배수법/희석법A/희석법B) 전체를 실제 실행해 Python 계산과 대조 검증.

### 2-9. 결과 리포트에 근거 표시 요청
결과지 하단에 "참고 기준 및 출처" 섹션 추가:
- 적정공기 기준 표
- 법적 근거 (성능기준만 규정, 구체적 수치 없음을 명시)
- 기술지침(권장 최소기준) — 계산방식별로 자동 전환
- 사업장(담당자) 결정값 안내 및 책임 소재 명시

### 2-10. 인쇄 여백 문제
사용자가 인쇄 결과 스크린샷을 첨부 — 여백이 전혀 없이 출력됨을 지적.
→ 원인: `@page` 규칙 누락. `@page{size:A4; margin:...}` 추가 후 **실제 PDF를 생성**해 픽셀 단위로 여백을 측정하여 검증(화면 캡처가 아닌 방식으로 검증한 것이 핵심).

### 2-12. 최종 수정 3건
1. **입력창 포커스 문제**: 정격풍량 등 숫자 입력 시 한 글자마다 포커스가 풀리는 문제 → `oninput`(글자마다 재렌더) 방식이 원인. `onchange`(다른 곳 클릭 시 반영) 방식으로 전면 전환하여 해결. 실제 타이핑 시나리오로 재현·검증.
2. **모바일 반응형**: PC/모바일 레이아웃 분기 추가. 375px 기준 가로 스크롤 없음, 송배풍기 표는 PC에서는 표, 모바일에서는 카드형으로 자동 전환.
3. **포스코 블루 컬러 적용**: POSCO 공식 CI 페이지에서 확인한 정확한 컬러(Main `#05507D`, Light Blue `#00A5E5`) 기반으로 팔레트 구성.

### 2-14. UX 개선 4건 (기획 후 진행)
사용자가 먼저 문제를 제기하고, 답변안을 검토받은 뒤 진행한 순서로 기록:
1. **모바일 크레딧 겹침**: 좁은 화면에서 제목 텍스트와 크레딧이 겹치는 문제 → 절대위치 대신 제목 위 줄에 자연스러운 흐름으로 배치 전환
2. **측정경과시간 단위**: 시간(h) 단위 입력이라 "10분=0.167" 암산이 필요했던 문제 → **분(min) 단위 직접 입력**으로 전환, 계산 시에만 내부적으로 ÷60 환산
3. **항목별 설명 부족**: 전문지식이 필요한 항목(분자량, TLV, 유효율 등)에 안내가 없던 문제 → ⓘ 클릭 시 펼쳐지는 설명 컴포넌트를 만들어 11개소에 적용 (다각형 좌표 입력법, MSDS 확인처 안내 등)
4. **임의 다각형법의 한계**: "도면 기반 전문가용 방식"이라는 지적에 따라, 다른 AI가 제안한 "구역 분할·합산" 아이디어를 검토·재구성해 **구역 조합형 체적 계산기**로 전면 개편
   - 사각기둥·원기둥·삼각기둥·원뿔대·사다리꼴 단면·임의다각형·직접입력 7종 형상을 구역 단위로 추가/삭제
   - 각 구역에 합산(+)/차감(−) 부호 지정 가능 (송배풍기 목록에 장비를 추가하는 것과 동일한 UX 패턴)
   - 유효공간율(%) 보정 기능 추가 — 단, 근거 없는 임의 하향 조정은 과소산정 위험이 있어 기본값 100% 고정 + 경고문구 필수 표기
   - 세션 저장 데이터 구조를 구역 배열(v2)로 변경, 구버전 세션 파일 자동 호환 처리

### 2-15. 체적 기본값 변경 + LEL(폭발하한계) 추가
- 구역 추가 시 기본 형상을 "사각기둥" → **"직접입력"**으로 변경 (드롭다운 순서도 맨 앞으로 조정)
- "적정공기 기준에 폭발하한계(LEL)도 있지 않냐, 5가지를 측정했는데?"라는 질의 → 실시간 검색으로 검증
  - **법정 기준(안전보건규칙 제618조, 4가지)**: 산소·CO₂·CO·H₂S — 법 조문에 구체적 수치 명시
  - **실무 추가기준(1가지)**: 가연성가스(LEL) 10% 미만 — 법 조문에는 없으나, 현장 5대가스 측정기의 표준 측정항목이며 KOSHA 산하 연구원 자료에도 준용 기준으로 언급됨
  - 두 기준을 뒤섞지 않고 "법정" / "실무 추가기준"으로 구분 표기하여 참조패널과 결과 리포트에 반영

## 3. 최종 기능 목록

### 3-1. 계산 엔진
| 방식 | 설명 | 산식 근거 |
|---|---|---|
| 체적배수법 | 최초 급기(체적×10배 이상) + 유지 환기(체적×20회/h 이상) | KOSHA GUIDE H-80-2021 9.1(1)항 |
| 희석법 A (발생량 입력) | 이상기체 몰부피 기반 희석환기 계산 | 일반 산업위생·환기공학 원리 |
| 희석법 B (측정 역산) | 질량보존식으로 발생량(G) 역산 후 필요환기량 산출 | 1구획 질량보존 모델 |
| 정상상태 도달시간 | 실제 배치 장비 기준 목표농도 도달 예상 시간 | 위 모델의 시간 해(解) |

### 3-2. 체적 계산기 (구역 조합형)
직접입력(기본값) / 사각기둥 / 원기둥 / 삼각기둥 / 원뿔대 / 사다리꼴 단면 / 임의 다각형(Shoelace 공식, 전문가용) — 구역을 계속 추가하며 합산(+)·차감(−), 유효공간율(%) 보정 지원

### 3-3. 송배풍기 매칭
보유 장비 등록 → 유효율 반영 실질풍량 계산 → 필요 대수·여유율 자동 산출, 풍량 단위 변환기(CMH·CMM·L/min·CFM) 포함

### 3-4. 세션 관리
공간명 입력 → JSON으로 전체 세션(구역별 입력값·팬 목록 포함) 저장/불러오기 → 다중 밀폐공간 이력 관리 가능 (구버전 세션 파일 자동 호환)

### 3-5. 결과 리포트
- 화면용/인쇄용 제목 분리
- A4 1페이지 최적화 (여백 14mm/13mm)
- 참고 기준 및 출처(법정 4항목 + 실무 추가기준 LEL, 가이드/사용자입력값 구분) 자동 표기
- 작성자·확인자 서명란

### 3-6. UI/UX
- PC/모바일 반응형 분기 (표 ↔ 카드형 자동 전환, 375px 오버플로우 없음 검증)
- 모든 입력값 "다른 곳 클릭 시 반영" 방식으로 통일 (포커스 유지)
- 포스코 블루 컬러 팔레트 (WCAG AA 명도대비 검증 완료)

## 4. 검증 방법 (일관되게 적용한 원칙)

이 프로젝트 전반에 걸쳐, 화면 캡처나 육안 확인에만 의존하지 않고 **자동화된 검증**을 우선했다.

- **계산 로직**: Python으로 동일 수식을 별도 구현해 도구 출력값과 전수 대조
- **인쇄/PDF**: Playwright로 실제 PDF를 생성한 뒤, PIL로 픽셀 단위 여백을 측정 (화면 캡처는 실제 인쇄 여백을 반영하지 않으므로 신뢰하지 않음)
- **접근성**: WCAG 명도대비 공식을 직접 구현해 모든 텍스트/배경 조합을 수치로 검증
- **반응형**: 실제 뷰포트 크기(375px 등)에서 `scrollWidth`/`clientWidth` 비교로 가로 오버플로우 여부 확인, `getComputedStyle`로 표↔카드 전환 여부 확인
- **회귀 테스트**: 매 수정 후 기존 시나리오(모드 A/B/C, 세션 저장/불러오기 등) 전체를 재실행해 부작용 여부 확인

## 8. APK 빌드 관련

### 8-1. 빌드 방식
Android Studio 없이, 커맨드라인 도구만으로 직접 빌드함:
1. Android SDK 커맨드라인 도구(`sdkmanager`)로 `platform-tools`, `build-tools;34.0.0`, `platforms;android-34`만 설치 (Gradle·전체 IDE 불필요)
2. HTML 도구 파일을 그대로 앱 자산(`assets/index.html`)으로 포함
3. `MainActivity.java` 하나로 전체 화면 WebView를 띄우고 `file:///android_asset/index.html`을 로드하는 최소 래퍼 작성
4. `aapt2`(리소스 컴파일·링크) → `javac`(자바 컴파일, JDK 21) → `d8`(DEX 변환) → `zipalign` → `apksigner`(서명) 순서로 수동 빌드
5. 서명은 개인 디버그 키(자체 서명)로 진행 — 구글 플레이 정식 배포용 키가 아님

### 8-2. 검증 내용
- `apksigner verify`로 서명 유효성 확인 (APK Signature Scheme v2·v3 통과)
- `aapt dump badging`으로 패키지명(`com.hsh.ventcalc`), 앱 라벨, 최소/타깃 SDK 버전(24~34) 확인
- 다만 **실제 안드로이드 기기·에뮬레이터에서의 설치·구동 테스트는 이 환경에서 할 수 없어 미실시** — 빌드 산출물의 구조적 유효성만 확인한 상태

### 8-3. 알려진 제약사항 (1차 빌드 당시 — 8-5에서 해결됨)
1차 빌드 시점에는 아래 기능이 WebView 특성상 동작하지 않을 것으로 예상되어 미검증 상태로 공유했으나, ***8-5 항목에서 네이티브 브릿지를 추가해 해결함***:
- ~~인쇄 / PDF 저장 버튼이 동작하지 않을 수 있음~~ → 해결
- ~~세션 JSON 저장/불러오기, 송배풍기 목록 내보내기가 동작하지 않을 수 있음~~ → 저장은 해결(불러오기는 파일 선택 방식이라 원래도 정상 동작)
- 다만 실제 기기에서의 최종 구동 테스트는 여전히 이 환경에서 할 수 없어 사용자 확인 필요

### 8-4. 설치 방법
1. `밀폐공간_환기량_산정_도구.apk` 파일을 안드로이드 기기로 전송(카카오톡 '나에게 보내기', 이메일, USB 등)
2. 파일을 탭하여 설치 시도 → "출처를 알 수 없는 앱" 차단 경고가 뜨면 설정에서 해당 앱(파일 관리자 등)의 설치 허용을 켜야 함
3. 자체 서명 인증서이므로 "확인되지 않은 앱" 경고가 표시될 수 있음 — 개인/사내 용도로 제작된 것이므로 정상적인 현상

### 8-5. 인쇄(PDF 저장) 및 세션 파일 저장 문제 해결
"HTML은 폰 브라우저에서 PDF 저장이 됐는데 APK는 왜 안 되냐"는 질의 → 원인 확인 후 수정:
- **원인**: 안드로이드 WebView는 `window.print()`(웹표준 인쇄)와 `<a download>`(Blob 다운로드)를 기본적으로 지원하지 않음. 크롬 등 정식 브라우저 앱은 이 기능을 자체 내장하고 있지만, 앱에 내장한 WebView는 별도 연결이 필요함
- **해결**: `MainActivity`에 `AndroidBridge`(자바스크립트 연동 클래스)를 추가
  - `print()`: `PrintManager` + `WebView.createPrintDocumentAdapter()`로 안드로이드 표준 인쇄 다이얼로그 연결(그 안에 "PDF로 저장" 옵션 포함)
  - `saveFile()`: `MediaStore`(Android 10+) 또는 공용 다운로드 폴더(구버전)에 JSON 직접 저장
  - HTML 쪽 `인쇄 버튼`과 `세션/장비목록 저장 함수`를 수정해, 앱 안에서 실행 중이면 위 네이티브 기능을, 일반 브라우저에서는 기존 방식(`window.print()`, Blob 다운로드)을 그대로 쓰도록 자동 분기 처리 → **브라우저 버전 동작에는 영향 없음(회귀 테스트로 확인)**
  - 빌드 중 D8 컴파일러(버전 8.2.2-dev)가 중첩 클래스(내부 클래스 안의 익명/멤버 클래스) 구조에서 `NullPointerException`을 일으키는 버그를 발견 → 모든 브릿지 클래스를 최상위(non-nested) 클래스로 분리하여 회피

### 8-6. 아이콘 개선
기본 팬 모양 아이콘이 "별로"라는 피드백 → 순환 화살표(포스코 네이비) + 4엽 팬 날개(포스코 라이트블루)로 재구성해 "환기" 느낌을 직접적으로 표현. 5개 해상도(mdpi~xxxhdpi) 모두 재생성.

### 8-7. "불러오기" 기능이 동작하지 않는 문제 해결
실제 기기에 설치 후 "저장은 되는데 불러오기가 안 된다"는 제보 → 원인 확인 후 수정:
- **원인**: 안드로이드 기본 `WebChromeClient`는 `<input type="file">` 파일선택창을 지원하지 않음. "저장"은 8-5에서 만든 별도 네이티브 기능이라 정상 동작했지만, "불러오기"는 웹 표준 파일 입력에 의존하고 있어 탭해도 아무 반응이 없었던 것
- **해결**: `AppWebChromeClient`(신규 클래스)에 `onShowFileChooser()`를 구현하여 안드로이드 표준 파일선택 인텐트를 직접 연결, `MainActivity`에서 결과를 받아 WebView에 돌려주도록 `onActivityResult()` 추가
- 함께 요청된 "JSON 불러오기 아이콘이 작다"는 피드백도 반영 — 저장/불러오기 버튼을 표준 크기로 확대하고 아이콘을 1.25배로 키움

### 8-8. 저장/불러오기 아이콘 크기 불일치 — 이모지 → SVG 전환
"PC에서는 저장/불러오기 아이콘 크기가 다르게 보이는데 폰에서는 똑같다"는 제보 → 원인 규명:
- **원인**: 💾, 📂는 폰트가 아니라 OS가 제공하는 이모지 폰트로 그려짐. Windows의 이모지 폰트(Segoe UI Emoji)는 두 이모지의 실제 그림 크기(잉크 영역)가 서로 다르게 설계되어 있고, 안드로이드의 이모지 폰트(Noto Color Emoji)는 우연히 비슷하게 보였을 뿐 — `font-size` 숫자를 조정하는 방식으로는 근본적으로 해결 불가능한 문제
- **해결**: 이모지를 전부 **인라인 SVG 아이콘**(stroke 기반, `currentColor` 상속)으로 교체. 벡터 그래픽이라 OS·브라우저와 무관하게 모든 환경에서 픽셀 단위로 동일하게 렌더링됨 → 실제 렌더링 후 두 아이콘의 bounding box가 16×16으로 완전히 일치함을 확인

### 8-9. "아이콘이 아니라 버튼 박스(높이) 자체가 다르다" — 근본 원인 재규명
8-8 조치 후에도 "사각 박스 높이가 다르다"는 재지적 → 아이콘이 아니라 **버튼 요소 자체의 렌더링 높이 차이**였음을 확인. 디버깅 과정을 단계별로 기록:
1. **1차 진단**: `<button>` 요소는 `<label>`과 달리 브라우저 기본값으로 폰트를 상속받지 않고 "Arial"로 렌더짐 확인 → `font-family:inherit` 추가했으나 **높이 차이(48.7px vs 43.7px) 그대로**
2. **2차 진단**: `<button>`의 `line-height`가 "normal"로 계산되어 페이지 전역 line-height(1.55)를 상속받지 못함을 확인 → `line-height:inherit` 추가했으나 **여전히 높이 차이 동일**
3. **3차 진단**: `<button>`의 네이티브 OS 외형(appearance)이 CSS 오버라이드와 무관하게 내부 여백을 추가로 가짐을 의심 → `appearance:none` 추가했으나 **여전히 변화 없음**
4. **격리 실험**: 숨김 파일 input을 DOM에서 강제 제거해도 높이 불변 확인 → 입력 요소는 원인이 아님을 배제
5. **최종 원인**: 크롬 브라우저의 `<button>` 네이티브 폼 컨트롤 렌더링 엔진이 CSS 박스 모델(padding/line-height/appearance) 조정만으로는 제거되지 않는 내부 여백(약 5px)을 가지고 있음 — padding 기반 높이 설계 자체가 요소 종류에 따라 불안정함을 확인
6. **최종 해결**: `.btn` 클래스를 **패딩 기반 높이에서 고정 `height` 값(44px, small은 36px)으로 전면 전환**. 요소 종류(button/label)나 폰트 렌더링 방식과 무관하게 항상 100% 동일한 높이를 갖도록 구조적으로 보장 → 실제 측정 결과 두 버튼 모두 정확히 44.0px로 완전 일치 확인
- 회귀 테스트: 긴 텍스트가 들어가는 다른 버튼들(6단계 마법사 이동 버튼 등)이 고정 높이로 인해 텍스트가 잘리지 않는지 `scrollHeight`/`clientHeight` 비교로 전수 확인 (문제 없음)

### 8-10. 버튼 완성도 전면 재점검 ("시킨 것만 고치지 말고 전체를 보라")
8-9에서 특정 버튼 쌍만 고친 뒤, 같은 종류의 높이 불일치가 다른 곳(5단계 툴바: "+ 장비 추가"·"풍량 변환기"는 36px인데 "JSON 내보내기/불러오기"만 44px)에도 남아있다는 지적 → **PC·모바일 전 화면의 버튼을 전수 조사**:
- 자동화 스크립트로 모든 단계(1~6단계)의 모든 버튼을 부모 컨테이너별로 그룹핑해 높이를 비교하는 검증 스크립트 작성 → 그룹 내 높이가 다르면 자동으로 플래그 표시되도록 구성
- **발견된 추가 문제 2건**:
  1. 5단계 툴바 4개 버튼("+ 장비 추가", "JSON 내보내기", "JSON 불러오기", "풍량 변환기") 중 2개만 `small` 클래스가 남아 있어 높이가 섞여 있었음 → 모두 일반 크기(44px)로 통일
  2. 2단계 "+ 구역 추가"도 동일하게 `small` → 일반 크기로 통일 (5단계 "+ 장비 추가"와 대응되는 동일 패턴이므로 크기도 맞춤)
  3. 모바일 전용 미디어쿼리의 `.btn` 규칙이 여전히 패딩 기반(`padding:12px 16px`)으로 남아있어, 데스크톱에서 고정한 방식(고정 height)과 불일치 → 모바일도 고정 높이(48px/42px)로 통일
  4. 구역 카드 내부(`.zone-card-head`)의 구역명 입력창·형상 선택창·합산/차감 토글·삭제 버튼 4가지 요소가 각각 38.9px/35px/35.4px/36px로 미세하게 들쭉날쭉했던 것도 모두 38px로 통일

## 9. Windows EXE 빌드

### 9-1. 방식
Android Studio 없이 SDK 커맨드라인으로 APK를 빌드했던 것과 같은 접근으로, Windows도 무거운 도구(Electron 등) 없이 가벼운 방식을 선택:
- `pywebview`(파이썬으로 OS 내장 웹 렌더러를 띄우는 라이브러리) + `PyInstaller`(파이썬 스크립트를 exe로 패키징)
- HTML 도구 전체(CSS·JS 포함, 76,656 bytes)를 **base64로 인코딩해 `app.py` 파이썬 스크립트 안에 직접 내장** → 별도 데이터 파일 없이 `app.py` 하나로 완결되도록 구성 (PyInstaller의 `--add-data` 경로 문제를 원천적으로 회피)
- Windows용 아이콘은 안드로이드용으로 만든 팬 이미지를 `.ico`(16~256px 6종 해상도)로 함께 변환·제공

### 9-2. 이 환경에서의 검증 한계와 실제 사용자 확인
이 환경은 Linux 서버라 Windows exe를 직접 실행해볼 수 없어, 아래까지만 자체 검증하고 나머지는 사용자가 직접 확인:
- Python 문법 검증, base64 왕복 시 원본 HTML과 완전히 일치하는지 바이트 단위 대조 (일치 확인)
- `pywebview.create_window()`에 넘긴 인자(`html`, `width`, `height`, `min_size`)가 실제 설치된 라이브러리 함수 시그니처와 일치하는지 확인
- 가상 디스플레이(Xvfb)로 실제 창 구동을 시도했으나 이 환경 자체가 멈춰(hang) 중단 → 라이브 GUI 구동 테스트는 결국 못 함

### 9-3. 사용자 환경에서 발생한 문제와 해결
1차 시도 시 `pyinstaller` 명령이 "내부 또는 외부 명령이 아닙니다" 오류로 실패:
- **원인**: pip가 설치한 실행파일(`pyinstaller.exe`)이 위치한 폴더(`...\Python\pythoncore-3.14-64\Scripts`)가 Windows PATH에 등록되어 있지 않아 cmd가 명령어를 찾지 못함. 스크린샷 로그에도 동일한 경고(`bottle.exe`, `cffi-gen-src.exe` PATH 미등록)가 이미 나타나 있었음
- **해결**: `pyinstaller` 대신 `python -m PyInstaller`로 실행 → PATH와 무관하게 현재 파이썬 인터프리터가 모듈을 직접 실행하므로 문제 해결
- **결과**: 사용자가 재시도 후 **빌드 성공 확인**

### 9-4. 사용법 요약 (최종)
```cmd
cd /d "C:\Users\updat\Downloads"
python -m PyInstaller --onefile --noconsole --name "VentCalc" --icon=icon.ico app.py
```
빌드 결과물: `dist\VentCalc.exe` (단일 실행파일, 파이썬 미설치 PC에서도 실행 가능)

### 9-5. "불러오기는 되는데 저장이 안 된다" 문제 해결
빌드 성공 후 실사용 중 "공간·송배풍기 저장이 안 된다"(불러오기는 정상)는 제보 → 원인 확인 후 수정:
- **원인**: pywebview가 쓰는 Windows 렌더링 엔진(WebView2)은 파일 **열기**(`<input type="file">`)는 OS 표준 창을 그대로 띄워주지만, 파일 **다운로드**(Blob 방식)는 앱이 별도로 다운로드 이벤트를 연결해줘야 동작 — 안드로이드 때와 동일한 유형의 문제가 이번엔 Windows 쪽에서 발생한 것
- **해결**: `app.py`에 pywebview의 `js_api` 기능으로 `Api.save_file()`을 추가 — 실제 Windows "다른 이름으로 저장" 창을 띄워 사용자가 지정한 위치에 저장. HTML의 저장 함수도 앱 환경(안드로이드/윈도우/일반 브라우저)을 자동 감지해 알맞은 방식을 쓰도록 분기 확장
- 빌드 시 `webview.SAVE_DIALOG`가 deprecated 경고를 띄우는 것을 발견해 최신 API(`webview.FileDialog.SAVE`)로 교체

### 9-6. 버튼 높이 통일 후에도 "JSON 내보내기" 클릭이 무반응 — 타이밍 버그 발견
버전 확인(버튼 높이가 통일된 것으로 최신 빌드임을 상호 확인) 후에도 재현됨 → 재조사:
- **원인**: pywebview는 창이 화면에 뜬 직후 `window.pywebview.api`(9-5에서 추가한 저장 기능)를 **비동기로 살짝 늦게** 연결함. 사용자가 창이 뜨자마자 바로 버튼을 클릭하면, `window.pywebview.api.save_file`이 아직 존재하지 않아 아무 동작도 하지 않고 **조용히 실패**하는 경합(race condition)이 있었음 — 이전 버전은 이 경우를 대비한 안내/재시도 로직이 전혀 없었음
- **해결**: `downloadOrSave()`에 재시도 로직 추가 — `window.pywebview`는 있는데 `.api.save_file`이 아직 없으면 0.2초 간격으로 최대 15회(약 3초) 재확인 후 자동 저장 시도. 3초가 지나도 준비되지 않으면 "저장 기능이 아직 준비되지 않았습니다. 앱을 재시작해 주세요"라는 명확한 안내를 반드시 띄우도록 변경 — **이제는 어떤 경우에도 완전한 무반응은 발생하지 않고, 성공/취소/오류/재시도 안내 중 하나가 반드시 표시됨**
- 검증: 브라우저에서 `window.pywebview.api`가 1초 뒤 늦게 나타나는 상황과, 끝까지 나타나지 않는 상황(타임아웃) 두 가지를 모의 실행해 재시도 성공과 타임아웃 안내 모두 정상 동작함을 확인

### 9-7. 재시도 로직 적용 후에도 여전히 무반응 — 1차 원인 추정(이후 9-8에서 정정됨)
9-6 조치를 실제 빌드해 테스트했음에도 "이 공간 저장", "JSON 내보내기" 모두 **완전 무반응**(9-6의 타임아웃 안내창조차 뜨지 않음) 재현 → 이는 `save_file` 함수 자체가 존재하지 않는 상황(9-6이 대응하는 경우)이 아니라, **함수가 호출은 되지만 Promise가 영원히 응답하지 않는 상황**임을 시사 → 화면에 실시간 진단 표시기를 넣고, 콘솔 창을 켠 채로(`--noconsole` 제외) 재빌드해 실제 상황을 확인하는 방식으로 전환:
- **1차 추정 원인**: PyInstaller의 `--noconsole` 옵션이 `sys.stdout`/`sys.stderr`를 `None`으로 만들어, 내부에서 이 `None`에 값을 출력하려다 백그라운드 스레드가 조용히 죽는 것으로 추정
- **당시 조치**: `webview.start(debug=True)` + 콘솔 창 유지로 재빌드 → 정상 동작 확인
- **배포용 정리(1차)**: 콘솔 창 대신 `sys.stdout`/`sys.stderr`가 `None`이면 더미 스트림으로 교체하는 안전장치만 추가하고, `debug=True`와 진단 코드는 모두 제거 → **그러나 이 배포판에서 동일 증상이 재발함 (9-8 참고)**

### 9-8. "디버그 켠 exe는 되는데 배포판은 또 안 된다" — 최종 정정
9-7의 "배포용 정리(1차)"에서 stdout 안전장치만 남기고 `debug=True`를 제거했더니, 저장 기능이 다시 무반응 상태로 돌아감 → **9-7의 원인 추정이 틀렸음을 인정하고 재조사**:
- pywebview 소스코드(`webview/__init__.py`의 `start()` 함수)를 직접 열어 확인한 결과, `debug=True`는 단순히 콘솔 로그 레벨(`logger.setLevel(logging.DEBUG)`)만 바꾸는 것이 아니라, **Windows용 EdgeChromium 백엔드의 초기화 방식 자체에 영향을 주는 것으로 판단됨** (정확한 내부 동작은 Windows 전용 백엔드 코드라 이 작업 환경에서 직접 실행·추적은 불가능했고, "debug=True일 때만 정상 동작한다"는 반복 재현 결과로 판단한 것임을 밝혀둠)
- **최종 결론**: `--noconsole` 자체는 문제와 무관했고(콘솔 유무는 착시였음), **`debug=True` 여부가 실제 스위치**였음
- **최종 조치**: 배포판에도 `webview.start(debug=True)`를 유지하기로 결정. `debug=True`는 콘솔 창을 강제로 띄우는 옵션이 아니므로 `--noconsole` 빌드와 함께 써도 창 없이 깔끔하게 동작함. stdout 안전장치는 해가 되지 않으므로 그대로 유지
- **남는 부작용**: `debug=True`이면 실행 창에서 마우스 우클릭 시 "요소 검사"(개발자 도구) 메뉴가 노출됨 — 사내 도구 배포 목적상 보안·품질상 문제는 없다고 판단해 그대로 유지하기로 함
- **정직하게 남기는 한계**: 왜 `debug=False`에서만 `js_api` 백그라운드 스레드가 응답하지 않는지, pywebview/WebView2 내부의 정확한 근본 기전은 끝내 규명하지 못함. 반복 재현 실험(디버그 on/off만 바꿔 교차검증)으로 확인된 **경험적 해결책**임을 명시함

### 9-9. DevTools 창이 자동으로 뜨는 문제 — 원인 분리로 해결
`debug=True` 적용 후 저장·내보내기는 정상 동작했으나, 실행할 때마다 별도의 "DevTools" 창이 화면에 자동으로 함께 뜨는 것이 배포판으로서 보기 좋지 않다는 지적 → pywebview의 Windows 백엔드 원본 소스(`webview/platforms/edgechromium.py`)를 직접 열어 확인:
- `debug=True`는 실제로는 4가지 WebView2 설정(브라우저 단축키, 기본 우클릭 메뉴, **DevTools 사용 가능 여부**, 상태표시줄)을 한꺼번에 켜는 스위치였고, 그와는 **별도로** `if _state['debug'] and webview_settings['OPEN_DEVTOOLS_IN_DEBUG']: sender.CoreWebView2.OpenDevToolsWindow()` 코드가 **DevTools 창을 자동으로 화면에 띄우는** 역할을 하고 있었음
- 즉 "DevTools 기능이 켜져 있는 것"과 "DevTools 창이 자동으로 보이는 것"은 서로 다른 설정으로 분리되어 있었음
- **해결**: `webview.settings["OPEN_DEVTOOLS_IN_DEBUG"] = False`를 `create_window()` 호출 전에 추가 — `debug=True`(저장 기능에 필요한 설정)는 그대로 유지하면서, 자동으로 창이 뜨는 것만 억제
- **남는 부수 효과**: 우클릭 시 "요소 검사(Inspect)"를 수동으로 실행하는 것은 여전히 가능함(개발자 도구 자체는 켜져 있으므로) — 다만 자동으로 튀어나오지는 않음
